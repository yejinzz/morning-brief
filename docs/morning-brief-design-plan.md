# Morning Brief — 설계 플랜 요청서

> Claude Code 전달용 · **설계 전용** · 프로젝트 `morning-brief`

## 1. 목표와 최우선 제약

개인용 모바일 뉴스 브리핑 서비스 **Morning Brief**를 설계한다. 매일 출근 전 5분 이내에 국내외 시사 및 개발·AI 분야의 중요 뉴스를 파악할 수 있도록 한다.

**최우선 요구사항은 월 운영비 0원이다.** 무료 체험 크레딧, 유료 구독, 유료 API, 유료 플랜, 결제 수단 등록이 필수인 서비스, 한도 초과 시 자동 과금되는 구성은 사용하지 않는다. 무료 한도가 소진되면 안전하게 작업을 중단하거나 기존 브리핑을 보여준다. 무료 서비스의 정책 변경이나 실행 지연 때문에 정확한 07:00 실행 및 영구적 무중단 운영을 보장할 수 없다는 점을 명시한다. 실제 무료 조건은 공식 문서로 검증하고 확인 일자를 기록한다.

이번 요청은 **설계 문서 작성만** 수행한다. 애플리케이션 코드 작성, 의존성 설치, DB 생성, 클라우드 리소스 생성, 배포 및 실제 구현 플랜 수립을 하지 않는다. 설계 보고 후 사용자 승인을 기다린다.

## 2. 제품 요구사항

### 2.1 뉴스 카테고리

1. **국내 시사** — 정부 정책, 법·제도, 사회 현안, 공공기관 발표
2. **경제·국제** — 금리, 물가, 환율, 거시경제, 국제 정세, 산업 변화
3. **AI·LLM** — 주요 모델, AI 에이전트, AI 기업·도구·정책
4. **개발·인프라** — Java, Spring Boot, React, Next.js, Python, Linux, Docker, DB, 클라우드, DevOps, 보안, 오픈소스
5. **기타 테크** — 반도체, 하드웨어, 모바일, OS·플랫폼, 신기술

### 2.2 수집·선정·분석

- 매일 **07:00 Asia/Seoul**을 목표로 클라우드 예약 실행한다. 사용자 PC와 스마트폰의 전원 상태와 무관하게 동작해야 한다.
- 최근 24시간 기사를 우선 수집하고, 부족하면 최대 72시간까지 확대한다.
- 카테고리별 후보 **10~20건을 목표**로 수집하되 무료 소스·호출 제한에 맞춰 조정한다.
- 공식 RSS, 합법적으로 사용 가능한 무료 뉴스 API, 공식 발표·기술 블로그를 우선 검토한다. 접근 가능성, 이용 약관, 발행 시각, 본문 제공 범위, 호출 제한을 실제 확인한다.
- URL 정규화, 제목 유사도, 동일 사건 그룹화, 이전 브리핑과의 중복 검사를 수행한다.
- **후보 수집 → 정규화·중복 제거 → 출처·관련성 필터 → AI 영향도 분석 → 카테고리별 최대 3건 선정 → HIGH만 표시** 순서로 설계한다. 최신 3건을 먼저 고정하고 분석하지 않는다.
- 최종 선정은 영향도·중요성·최신성·출처 신뢰도·개발 실무 관련성을 고려한다. 하루 최대 15건이며 3건을 억지로 채우지 않는다.
- AI는 `HIGH / MEDIUM / LOW`를 분류하고 근거, 3문장 이내 요약, 개발자 관련성을 구조화된 JSON으로 반환한다. HIGH는 광범위한 사회·경제 영향, 중대한 정책 변화, 중요한 AI 플랫폼 변화, 심각한 보안 취약점, 개발 실무에 직접적인 변화를 주는 소식 등에 한정한다.
- AI가 확인하지 못한 사실을 생성하지 않으며, 제목·설명만으로 분석했다면 근거 한계를 표시한다. 검증 불가·출처 충돌 시 보류 또는 별도 상태로 처리한다.
- HIGH가 없으면 임의 승격하지 않는다. 최종 선정 결과 및 비노출 분석 결과는 저장하되 기본 UI에는 HIGH만 노출한다.
- 당일 HIGH 기사로 **오늘의 한 줄 브리핑(1~2문장)**을 만들고 예상 읽기 시간을 표시한다. 전체 기본 브리핑은 5분 이내 분량을 목표로 한다.

### 2.3 모바일 PWA

- React + Vite + TypeScript + Tailwind CSS 기반 **모바일 우선 PWA**를 우선 검토한다. Android·iOS 홈 화면 설치, 데스크톱 브라우저 조회도 고려한다.
- 기본 화면: 날짜, 생성 완료 시각, 한 줄 브리핑, 수집 수·HIGH 수·예상 읽기 시간, 뉴스 목록.
- 탭: **전체(기본) / 국내 시사 / 경제·국제 / AI·LLM / 개발·인프라 / 기타 테크**.
- 카드: 제목, 카테고리, 3문장 이내 요약, HIGH 판단 근거, 출처, 발행 시각, 원문 링크.
- 지난 날짜 브리핑, 읽음 상태, 관심 카테고리, 알림 설정, 라이트·다크 모드.
- 로딩, 생성 중, HIGH 0건, 카테고리 0건, 네트워크 오류, 마지막 정상 브리핑, 오프라인 캐시 상태를 정의한다.
- 과도한 대시보드 카드·장식·여백보다 빠른 읽기와 정보 밀도를 우선한다.

### 2.4 Web Push

- **07:00에 앱을 강제로 실행하지 않는다.** 클라우드에서 브리핑을 생성하고 **정상 완료 후** Web Push를 보낸다.
- 알림: `오늘의 주요 뉴스 N건`, 카테고리별 HIGH 건수, 예상 읽기 시간. 누르면 해당 날짜 브리핑으로 이동한다.
- 명시적 권한 동의, 구독·해지, VAPID 키 관리, 만료 구독 제거, 실패 재시도, 날짜·사용자별 중복 발송 방지.
- 브리핑 생성 실패 시 성공 알림을 보내지 않는다. HIGH 0건 알림 여부는 설계 결정 항목으로 제시한다.
- iOS 홈 화면에 설치된 웹 앱에서의 푸시 지원 조건, 브라우저·OS별 제약, HTTPS 요구사항을 검증한다.

## 3. 권장 검토 아키텍처

- **프론트엔드:** React / Vite / TypeScript / Tailwind / PWA 플러그인
- **호스팅:** Cloudflare Pages Free 등 무료 정적 호스팅
- **뉴스 파이프라인:** Python + RSS/무료 공식 API
- **AI:** 무료 사용 한도가 있는 Gemini API 등; 기본 모델 하나, 추후 교체 가능한 단순 어댑터
- **DB·인증:** Supabase Free + PostgreSQL + Auth 또는 더 적합한 무료 대안
- **예약 실행:** GitHub Actions 무료 사용량 또는 무료 스케줄러
- **알림:** 표준 Web Push + VAPID

이 목록은 **후보**이지 확정 스택이 아니다. 공식 문서 기준으로 현재 무료 조건과 한도를 확인하고, 대안을 비교하여 선정한다. 서비스 계정·결제 수단을 생성하지 않는다.

### 3.1 아키텍처 검토

- 스케줄러 → 수집 → 정규화 → 사전 필터 → AI 평가 → 선정 → 브리핑 저장 → 푸시 발송 흐름과 실패 분기를 시퀀스로 정의한다.
- PWA 조회와 서버 측 배치를 분리한다. AI 키·서비스 권한 키는 브라우저에 전달하지 않는다.
- GitHub Actions 예약 실행 지연·누락, UTC cron과 KST 변환, 수동 재실행, 멱등성, 재시도, 로그를 설계한다.
- Supabase Free의 비활성 프로젝트 일시 중지 가능성 및 데이터 복구 전략을 검토한다.
- GitHub Actions에서 직접 Web Push를 발송하는 방식과 무료 서버리스 함수 방식 등을 비교한다. 무료 한도와 비밀키 저장 방식을 확인한다.
- 무료 운영이 어려운 기능은 비용을 발생시키지 않는 축소·대체안을 제시한다.

## 4. 뉴스 품질 및 AI 정책

### 4.1 뉴스 소스 평가표

각 후보 소스마다 출처, 카테고리, URL, 제공 형식, 무료 사용 조건, 이용 약관, 호출 제한, 발행 시각 제공, 본문 접근, 장애 대체 소스를 기록한다. Google News RSS, 국내 언론사 RSS, 공공기관 발표, Hacker News, GitHub Releases, 공식 개발·AI 블로그 등을 검토하되 무조건 사용하지 않는다.

### 4.2 AI 비용·품질 통제

- 중복·저품질 기사를 AI 호출 전에 제외한다.
- 기사 여러 건의 묶음 분석과 단건 분석을 비용·오류 복구 관점에서 비교한다.
- 요청 수·토큰 수·실패 횟수에 **일일 상한**을 둔다.
- 유료 모델로 자동 폴백하지 않는다.
- 무료 한도 소진 시 작업을 중단하고 상태를 기록하며 마지막 정상 브리핑을 유지한다.
- AI 응답 JSON Schema, 분류 기준, 판단 근거, 모델 버전, 분석 시각을 정의한다.
- 기사 원문을 무단 재배포하거나 저작권을 침해하는 장문 저장을 하지 않는다. 제목·메타데이터·짧은 독자적 요약·원문 링크 중심으로 설계한다.

## 5. 데이터 및 보안 설계

아래 엔터티의 필요성·관계·제약·인덱스를 검토한다. 개인용 MVP에 불필요한 테이블은 합치거나 제외할 수 있다.

- `news_articles`: 원본 메타데이터, canonical URL, source, published_at, category, 수집 시각, 중복 그룹
- `news_analyses`: 기사별 모델, 영향도, 요약, 판단 근거, 개발자 관련성, 분석 시각·상태
- `daily_briefings`: 날짜(KST), 한 줄 요약, 수집 수, HIGH 수, 예상 읽기 시간, 생성 상태·완료 시각
- `briefing_articles`: 날짜별 선정 기사, 카테고리, 표시 순서
- `collection_jobs`: 실행 ID, 날짜, 상태, 단계별 건수, 실패·재시도, 시작·종료 시각
- `push_subscriptions`: 사용자·기기별 구독 엔드포인트·키, 활성 상태, 최종 전송 상태
- `user_preferences`: 카테고리, 테마, 알림 설정
- `notification_deliveries` 또는 동등한 발송 이력: 날짜별 중복 전송 방지
- 읽음 상태 저장은 DB와 로컬 저장 중 개인용 운영에 적합한 방식을 비교한다.

**보안 원칙:** 개인 계정 1개, 공개 회원가입 비활성화, Supabase Auth 등 최소 인증, 인증된 사용자만 조회, RLS, 서버 전용 비밀키, 최소 권한, 푸시 구독 정보 보호. 인증을 추가함으로써 PWA의 푸시·오프라인 동작에 생기는 영향도 검토한다.

## 6. 무료 운영 검증 — 필수

각 구성 요소마다 다음 표를 작성한다.

| 구성 요소 | 후보 서비스 | 공식 무료 한도·조건 | 예상 일·월 사용량 | 초과 시 동작 | 결제 수단 필수 여부 | 과금 위험 | 무료 대안 |
|---|---|---|---|---|---|---|---|

**통과 기준:** 유료 서비스 호출·자동 결제·유료 체험 크레딧 의존이 없고, 한도 초과 시 안전하게 멈추는 구성이어야 한다. 무료 플랜의 정책 변경으로 영구 0원을 보장할 수 없다면 그 위험을 명확히 보고한다.

추가로 검토할 사항:
- GitHub Actions 공개/비공개 저장소에 따른 무료 사용량·제약
- AI 무료 모델의 이용 조건·요청 제한·데이터 처리 정책
- DB 무료 용량·비활성 중지·백업 가능성
- 정적 호스팅의 빌드·트래픽 한도
- Web Push 발송 인프라와 VAPID의 실제 운영 제약
- 도메인 구입 없이 무료 서브도메인·HTTPS 사용 가능 여부

## 7. 예외 처리 및 운영

- 소스 장애: 다른 무료 소스로 대체하거나 해당 소스만 건너뛴다.
- AI 장애: 제한적 재시도, 개별 기사 실패 격리, 분석 미완료 표시.
- 배치 장애: 단계별 로그, 수동 재실행, 동일 날짜 중복 실행 방지.
- 부분 성공: 완료 기준을 명시하고, 불완전한 결과에 성공 알림을 보내지 않는다.
- 푸시 장애: 브리핑 저장 성공과 발송 실패를 분리, 제한적 재시도, 구독 정리.
- 무료 한도 초과: 자동 과금 없이 중단, 마지막 정상 브리핑 유지.
- 장기 운영: 데이터 보관 기간, 로그 보관, 장애 확인·복구, 무료 정책 재검토 방법.

**승인 전에는 구현 플랜 작성, 코드 수정, 패키지 설치, DB 생성, 배포를 진행하지 않는다.** 검증 불가능한 무료 조건은 추측으로 확정하지 않고 `확인 필요`로 표시한다.
